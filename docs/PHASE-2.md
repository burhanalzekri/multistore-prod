# المرحلة الثانية — قاعدة البيانات والمخطط متعدد المتاجر

## ما أُنجز

- توسعة Prisma/PostgreSQL من Shop/User تأسيسيين إلى **37 جدولاً** و**14 enum** تغطي نطاق البيانات المطلوب.
- إضافة نماذج Auth.js القياسية (`User`, `Account`, `Session`, `VerificationToken`) تمهيداً لتنفيذ المنطق في المرحلة 4.
- النطاق التجاري: متاجر وعضويات، منتجات ومتغيرات وصور وفئات، عملاء وعناوين، طلبات وبنود وسجل حالات، كوبونات وعروض، نقاط ولاء ومراجعات وقوائم رغبات، SMS وحملات بريد وسجل نشاط وإعدادات، خطط واشتراكات.
- نماذج مساندة للإعدادات والمراحل التالية: مناطق وأسعار شحن، قواعد ضرائب ووسائل دفع (إعدادات عامة فقط)، أصول وسائط، Webhooks، مفاتيح API، واشتراكات Push.
- **104 فهرساً**: مفاتيح tenant، slug، email، status/createdAt، علاقات البحث والقوائم، وعناوين الفهارس المركبة الشائعة.
- `shopId` ممثل في قاعدة البيانات كـ`shop_id`. جداول المجال متعددة المستأجرين لها فهارس/قيود tenant؛ والعلاقات المركبة في المنتجات والفئات والطلبات والعملاء تمنع ربط صف بكيان من متجر آخر على مستوى قاعدة البيانات.
- أكواد المتجر والنطاق المخصص فريدة؛ slug المنتج والفئة ورقم الطلب/كود الكوبون فريد داخل المتجر؛ البريد الفريد لحساب Auth.js عام، وبريد العميل فريد ضمن المتجر.
- قيم الخطط والأسعار غير معبأة: `Plan.isActive=false` والأسعار nullable إلى أن يوافق مالك المشروع على الأسعار. لا تُخزن أسرار الدفع كنص؛ إعداد الدفع `publicConfig` فقط، والحقول الحساسة مشفرة/مجزأة عند ربطها.
- إنشاء migration تأسيسية: `prisma/migrations/20261009222000_initial_schema/migration.sql` مع `migration_lock.toml`.
- إضافة `prisma/seed.ts` idempotent لبيانات توضيحية محلية اختيارية. لا يكتب بيانات افتراضياً، ويُمنع في الإنتاج؛ يحتاج `ALLOW_DEMO_SEED=true` صراحةً.

## التحقق

- `bun run db:validate` — ناجح.
- `bun run db:generate` — ناجح، Prisma Client 6.19.3.
- `bun run typecheck` — ناجح بعد توليد العميل.
- `bun run lint` — ناجح.
- `prisma migrate diff --from-empty --to-schema-datamodel ... --script` — يولّد 37 جدولاً و104 فهرساً.
- مقارنة إعادة التوليد مع ملف migration — متطابقة.
- `bun run db:seed` دون مفتاح تفعيل — يتخطى البذر كما هو مقصود.

## ما لم يُنفّذ بعد

لا توجد بيانات اعتماد Neon أو قاعدة متصلة في الجلسة؛ لم تُطبّق migration على قاعدة فعلية ولم تُنشأ بيانات تجريبية هناك. أوامر `db:migrate` و`db:migrate:deploy` تحتاج `DATABASE_URL` و`DIRECT_URL` صالحين. إعداد Neon الإنتاجي ونشر migration جزء من المرحلة 12. عزل الاستعلامات في طبقة التطبيق واختبارات منع تسرب البيانات مرحلة 3؛ هذا المخطط يضيف قيوداً مرجعية tenant-safe لكنه لا يغني عنها.

## أوامر الاستخدام بعد إعداد PostgreSQL

```bash
bun run db:validate
bun run db:generate
bun run db:migrate          # بيئة تطوير متصلة
bun run db:migrate:deploy   # تطبيق migrations المنشورة
ALLOW_DEMO_SEED=true bun run db:seed  # تطوير فقط، ممنوع في الإنتاج
```
